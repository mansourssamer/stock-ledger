# Stock & Ledger

Shoe wholesale by the box: stock, sales, customers, purchasing and accounts. This is the new
version of the Flask app, rebuilt as one page that runs on the phone itself.

- Opens instantly and every tap is instant: the data is on the device, not on a server.
- Keeps working without internet. Changes are saved on the device and upload by themselves
  when the connection returns, even if the app was closed in between.
- Data lives in the business's own Firebase project (Google). Free at this business's size.
- Hosted free on GitHub Pages. Screens in French, with an English switch; customer documents
  are always French.

## How it works

**Same tables, same SQL.** The app keeps a SQLite copy of the data in memory on the device,
with the old app's 43 tables and columns. Screens and reports run the old app's SQL on it, so
stock, values and balances come out exactly as before (`tests/compare.py` checks this against
the Python app). Ids imported from the old app stay numbers; records made here get text ids
like `n20261120143055123k0ab` that sort after them, by time.

**Firestore holds the rows in buckets.** Each table is a Firestore collection whose documents
hold about 200 rows: `{rows: {id: row}, updatedAt}`. Old rows go in bucket `i<id ÷ 200>`, new
rows in pages of 200 per day (`n20261120aa`, `n20261120ab`…), which keeps every document far
below Firestore's limits (1 MiB and 40,000 index entries) even on the day a container arrives.
Orders and purchase orders made here get their number when made (`ref_numbers`), so it never
changes and backups give the old app the same numbers. A sale touching 40 boxes is a few document writes, and
the whole business fits in a few hundred documents — far inside the free quota (50,000 reads
and 20,000 writes a day).

**Sync.** On start the app reads the device's own Firestore copy (instant, free, offline),
fills SQLite, then listens only for buckets changed since the last visit. A change is written
to SQLite at once and uploaded in the background; Firestore queues it while offline.

**Changes.** An operation (a form) runs the old app's SQL on the device copy inside one SQLite
savepoint: either all of it happens or none of it (a refusal rolls it back). Triggers note every row
it touched, and only those rows are uploaded. Ports of the old handlers live in `js/ops/`.

**Photos and documents** have their own collections (`images`, `files`), one document each,
fetched only when shown. Photos are shrunk to phone size; documents over 700 KB can't be kept
(Firebase Storage needs the paid plan since February 2026).

## One-time setup

1. **Firebase project** on your own Google account: console.firebase.google.com → Add project.
2. **Database**: Firestore Database → Create database → Standard edition → `europe-west1` →
   production mode.
3. **Sign-in**: Authentication → Sign-in method → enable **Google** and **Email/Password**. Google sign-in
   may not open in an app added to an iPhone's home screen, so the phone signs in with email and a
   password: set it in the app under Settings → Account → Set a password (it's added to the same account).
4. **Web app**: Project settings → Your apps → `</>` → register. Copy `firebaseConfig` into
   `config.js`.
5. **Rules**: Firestore → Rules → paste `firestore.rules`, replace `OWNER_EMAIL` with your email
   in lowercase → Publish.
6. **Hosting**: push this folder to a GitHub repository → Settings → Pages → deploy from the
   `main` branch, root folder. The address is `https://<user>.github.io/<repo>/`.
7. **Allow the address for Google sign-in**: Authentication → Settings → Authorized domains →
   add `<user>.github.io`.
8. **Import**: open the app → Importer les données → choose the backup .zip from the old app's
   Backup page. The app uploads everything, reads it back and compares it with the backup.

## Switching over from the old app

1. In the old app, stop entering anything, then Backup → **Download a backup now**.
2. In this app, **Import data** → choose that .zip. If this app already has data, the screen
   shows how many records the import adds, changes and removes, and the newest entry on each side
   (an older backup is flagged in red). Records entered in this app are listed, and the import
   stays locked until **Download a copy of this app first** has saved them
   (`stock-ledger-before-import-….zip`, an ordinary backup that imports back).
3. Tick **Replace all data…** → **Import now**. The app uploads, reads everything back and compares
   it with the backup row by row, plus stock value, what customers owe, cash and boxes in stock.
4. Green banner → from now on enter everything here. Keep the old app untouched for a few weeks
   as a fallback; this app's backups restore into it (Backup page → Restore) if ever needed.

## Backups

Settings → Download a backup gives one .zip: `erp.db` (all the data, in the old app's own format —
records made here are numbered after the old ones), `uploads/products/` (photos) and
`uploads/documents/`. Import data in this app reads it; the old app's Backup page restores it.

## Updating the app

Change the files, run `python3 tools/stamp_sw.py` (it fingerprints the files so phones fetch
the new version), push to GitHub. Phones switch to the new version the next time the app
opens with internet.

## Tests

- `tests/diff_run.sh OLD_APP_DIR erp.db workdir [maker]` — runs the same steps through the old Python app
  and through the new app, then compares every table row by row. `tests/scenario_make.py` (default) covers
  selling; `tests/scenario_make_buy.py` covers purchasing (suppliers, purchase orders, size runs, costs,
  payments, receiving and un-receiving, shipments, locations, price list); `tests/scenario_make_money.py` covers
  money (currencies, rate corrections that re-value what was booked, accounts, transfers, partners, expenses).
- `python3 tests/report_ref.py OLD_APP_DIR erp.db ref.json spec.json`, then `node tests/report_js.mjs erp.db spec.json > new.json`
  and `python3 tests/report_compare.py ref.json new.json` — every report and money page of both apps, value by value.
- `python3 tests/buying_ref.py OLD_APP_DIR erp.db DAY > old.json`, `node tests/buying_js.mjs erp.db DAY > new.json`,
  `python3 tests/buying_compare.py old.json new.json` — the buying plan of both apps, value by value.
- `node tests/e2e_sell.cjs backup.zip outdir [--phone]`, `node tests/e2e_buy.cjs backup.zip outdir [--phone]` —
  click through selling and purchasing in a browser; `tests/e2e_money.cjs` money and reports; `tests/e2e_crm.cjs` the CRM,
  proformas and settings, then downloads a backup and imports it into a fresh app.
- `tests/scenario_make_crm.py` (with `diff_run.sh`) — CRM and proformas through both apps.
- `node tests/backup_check.mjs new.db backup.db` — the backup database from a database this app made; the old app's
  figures on it (`tests/py_reference.py`) match the old app's own.
- `node tests/offline.cjs backup.zip outdir` — opens the app with no network (and checks every file is kept on the device).
- `node tests/e2e_container.cjs backup.zip outdir [boxes per mix]` — a whole container received in one go, with the test
  Firebase refusing anything the real one would (1 MiB and 40,000 index entries per document, 500 writes and 10 MiB per commit).
- `python3 tests/bucket_limits.py new.db` — every Firestore document a database makes stays inside those limits
  (`tests/scenario_make_container.py` with `diff_run.sh` makes a 1,000-box container day through both apps).
- `node tests/ids_check.mjs` — ids, day pages, and order numbers that never change once given.
- `tests/csv_compare.sh OLD_APP_DIR erp.db workdir` — the CSV exports of both apps, cell by cell.
- `node tests/e2e_auth.cjs outdir` — signing in: a password for the phone, a Google popup that fails, forgotten password, confirming an email.
- `node tests/e2e_extras.cjs backup.zip outdir [--phone]` — CSV buttons, voiding an invoice, the open boxes page.
- `node tests/sweep.cjs backup.zip outdir [--empty | --new-records]` — every screen in French and English, computer and phone:
  page errors, "undefined"/"NaN", raw ids, sideways scrolling, hidden text, texts with no French.
- `node tests/e2e_switch.cjs backup.zip older.zip outdir [--phone]` — the switch-over: same backup twice changes nothing,
  a record entered here blocks the import until the copy is downloaded, the copy brings it back, an older backup is flagged.

- `node tests/e2e.cjs backup.zip outdir [--phone]` — imports a backup into a fake Firebase,
  checks the report, visits the screens and saves screenshots.
- `python3 tests/py_reference.py OLD_APP_DIR erp.db > ref.json`, then
  `node tests/js_figures.mjs erp.db > new.json` and `python3 tests/compare.py ref.json new.json`
  — the old app's figures against the new app's, value by value.
